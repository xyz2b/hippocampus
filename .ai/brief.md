# Brief：M1 第 4 项 — 可见性与最小并发（解除 MCP 全局锁对模型调用的占用）

日期 2026-10-04，HEAD `fd7bffe`。用户 2026-10-04 同意开始。

## 背景
写入新路径（write_pipeline=w4_runtime_v1）与召回新路径（recall_pipeline=recall_v3）的离线与 CLI 部分已完成。MCP 服务（src/bin/pmr-mcp.rs）在整次调用期间持有服务全局锁（pmr-mcp.rs:67、:182），模型调用也在锁内，因此：
- 写入新路径在 MCP 上只允许 off/deferred，inline 启动即报错（J6）；
- 召回新路径在 MCP 在线调用时明确报错（W8）。

## 目标（target-design 2.5、2.6）
1. 模型调用（W1/W3/W4 后台、R1/R4 前台）不得在服务全局锁内进行；前台读取快照与后台提交只在必要的短临界区协调。
2. 后台整理任务可恢复且不重复执行：持久化在原文记录，按租约与预算认领；重启后恢复未完成任务；相对时间用接收时间；提交沿用快照、顺序屏障与删除检查（多数已在第 ②③ 段具备，需在 MCP 进程内接通后台执行）。
3. MCP 在线可用：写入新路径的 inline/后台模式、召回新路径的在线 R1/R4 解除报错。
4. **最小并发检查**（2.5）：用受控延迟的模型响应让一个后台任务保持未完成，同时发起前台召回；前台必须在释放后台响应之前完成，并通过 2.6 的新信息可见性检查。
5. **2.6 可见性验收**至少覆盖：旧记录“住上海”、本轮“已搬到南京”时原文立即可用且不给确定的上海当前值；本轮仅假设搬家时不误更新；后台失败、相关新原文被截断、两条更新乱序完成、处理跨日、来源删除时状态都正确呈现。

## 产品约束
- 默认路径（legacy）行为与输出不变。
- 不真实调用模型；用受控延迟的 mock。
- 删除与授权检查不放松；晚到结果不得恢复已删除内容。
- 数据库升版、冻结契约变更、默认切换需用户批准。
- P95 延迟的完整负载验收不在本项（target-design：基线后进行）；本项只做最小并发检查。

## 请 Codex 评审
- 现状：pmr-mcp 的锁结构、ChatMemoryService 的可变借用、SqliteMemoryStore 连接模型（单连接？），后台执行器（deferred drain）现在怎么跑；哪些已满足、哪些缺。
- 最简单可行方案（例如：服务内部拆成“读快照/短事务”与“模型调用在锁外”的两阶段；或每请求独立 SQLite 连接 + WAL；后台 worker 线程按租约认领），风险与替代方案。
- 分段计划（每段小而可独立提交），每段验收标准（含上面的并发与可见性检查）。
- 需要用户决定的事项。

## M1.5 真实使用修复（2026-10-06，依据 AF36–AF39）
目标：让“带孩子出行”这类真实对话能被正确记住并跨会话召回，原话无需重说。
范围：P0 宿主路由（工具描述 + ChatGPT 指令：bootstrap 后继续处理同一消息、个人陈述用 prepare 保存、具体问题另调 recall、不擅自 offline=true）；P0 来源状态查看 + 主体确认 + 未提交候选重建；P0 计划记忆（speech=plan 可提交，召回标注为计划，预订事实单列，修改/取消由模型判断更新）；P1 W1/W3 限定语遗漏修正；P1 历史原话补录；P2 W1 low 对照。
不做：自动受限实体、prepare 只读模式、用用户私有原话发送模型。
验收：去标识 MVP（4 条消息 + 2 次跨会话查询，≤24 次真实调用）——原话可追溯、限定语完整、计划明确标注、无需重说、删除后不能恢复；全套 0 失败；59/4 历史核验不变。

# Brief：本地轻量版可行性验证（AF384）

日期 2026-10-22，HEAD `ae7a7fd`（工作区另有 AF383 Inspector 改动待 Claude 复核，本任务不触碰）。用户 2026-10-22 同意方向与下列决定。背景分析见 docs/architecture/current-flow-and-gaps.md。

## 背景
- 成本：生产实测约 ¥0.27/条消息（AF350），输出 82%、推理 76%；直接降到 minimal 质量明显退化（AF354）。用户判断：个人记忆若成本高没人用，系统也过于复杂。
- 本地模型跑现行重契约不可用：AF148 W1/W3 合计 9B 关思考 12/80（W1 0/40）、27B 关思考 38/80、27B 开思考 27/40 但单次约 600 s；AF251 qwen3.8 R1 15/40、R4 28/48。
- 结论：不是把现有流水线换本地模型，而是围绕小模型能做好的事重新分工。

## 用户已定
1. 目标：大部分电脑本地可部署的模型能处理。本机 M4 32GB（Ollama：qwen3.5:9b-q8_0、qwen3.8:27b-q4_K_M-ctx64k、bge-m3、qwen3-embedding:0.6b）；普通 16GB 机器按 4B–9B 档为下限。
2. 分工：专用模型做识别/分类/匹配；本地小 LLM 生成笔记与画像；宿主大模型推理与作答；代码记账（片段核对、时间算术、删除、授权）。
3. 专用模型先只加两个：重排（bge-reranker-v2-m3 类）与 NER（GLiNER 类）；向量已有；分类模型等有训练数据（可由现有录制与标签蒸馏）再加。
4. 运行方式：ONNX 在 Rust 内运行（ort crate），不引 Python 辅助进程。
5. 中文效果必须实测；专用模型只做识别标注，不手写中文句式规则，歧义仍交 LLM/宿主。

## 目标（零云端费用验证）
- Q1 写入：极简笔记格式下，本地 9B / 27B（关思考）提取是否可用。A 组：仅 LLM；B 组：NER + 时间解析预标注后再交 LLM。
- Q2 召回：FTS + 向量 + 重排，取回原话/笔记交宿主，对比现有 R1/R4 路径的证据覆盖（检索层面零调用；若需宿主模型作答对照，另报次数与费用）。
- Q3 工程：重排与 GLiNER 能否导出 ONNX 并在 Rust ort 中跑通中文；延迟、内存、二进制/模型体积、Apple Silicon 加速（CoreML EP）可行性。

## 笔记格式草案（供评审）
`{subject_text, kind: fact|preference|plan|event|habit, note: 一句话, quote: 原话连续片段, time_text?, uncertainty_text?, condition_text?}`；代码核对 quote 逐字存在，时间由 temporal.rs 换算，无法换算保留原文。无逐条核验（W3）与逐条更新判定（W4）；新旧由召回时按时间排列交宿主判断。

## 范围
验证工具与报告放独立目录；可复用现有样本（W1/W3 标签 AF311/AF342/AF352 等）、评分与回放框架。真实会话样本只在本机使用，不外发。

## 不做
不改生产默认路径、冻结契约、DB；不删除现有代码；不调用云端模型（例外须另行报批）；不做画像巩固（下一步）。

## 请 Codex 评审
- 方案漏洞、风险与更简单的替代（例如 Q1 是否需要 B 组、笔记字段是否过多/过少）。
- ONNX/ort 风险：模型导出与 tokenizer、Rust 依赖与构建、CoreML、模型分发方式。
- 样本与评分口径如何复用；初步成功线建议（Claude 草拟：9B 在 W1 样本“该记内容覆盖 + 片段正确 + 限定语保留”≥30/40，即约现行 DS-Pro 37/40 的 80%）。
