# hippocampus 路线图

本文根据 `docs/architecture/` 的现状分析和 S6 首批留出结果，整理系统下一阶段的目标、方向和里程碑。日期：2026-09-28。

## 1. 目标

hippocampus 要成为 AI 的记忆中枢：保存用户原话，记录信息如何随时间变化，在需要时找回相关上下文，并提供可追溯的来源。

- **现在**：以 MCP 服务的形式接入各种聊天工具。
- **之后**：成为独立应用，采集用户的线上活动，从中提取记忆，让 AI 基于这些记忆回答问题、更懂用户。

已定的两个前提：

| 事项 | 决定 |
| --- | --- |
| 模型部署 | 由用户配置，目标形态是云端与本地混合 |
| 第一批数据源 | 用户与 AI 的对话 |

## 2. 现状判断

### 2.1 应保留的基础

- **信任边界清晰**：原文与事实分成两个事务保存（T1、T2）；证据由运行时注入；核验快照绑定候选的全部字段。
- **版本与时间建模扎实**：有语义槽和版本链，冲突时不替用户选边，“何时得知、何时成立、何时淘汰”分开记录。
- **可观测性与评测纪律强**：有调用预算账本、诊断 Trace、Inspector；留出集冻结，出错即停。

### 2.2 核心问题：复杂度放错了位置

S6 首批留出（`docs/refactor/s6/holdout-live-20260927-v1`）同时出现了两类相反的失败：

1. **写入过松**：原文是“雾岚打印机的默认纸张规格是A4。”，模型给出 `boolean=false`，系统把它当作事实提交。
2. **召回过严**：有证据的问题被拒答。入库时保留了“画速写时”这个活动条件，查询没有带上它，正确事实被过滤掉。

原因是分工放反了：

- **写入侧**让模型填约 25 个字段，再做 9 个维度的核验。一句话要 25 到 150 秒，格式也容易出错。
- **召回侧**靠约 5400 行中文句式规则做语义判断，换个说法就拒答。

过程上，`docs/refactor/s5/` 在两天内出现了约 60 个修复、实测、回归目录。逐个样本修补已经在逼近局部最优，泛化能力却没有提升。

## 3. 总体方向

### 3.1 以原文为本，结构化记忆只是索引

原始事件（原话、活动）是唯一的权威数据。结构化记忆降级为派生索引，可以随时从原文重建。这样带来三个好处：

- 提取出错只是索引错了，可以重新提取，不必每句话都做一次重型核验；
- 可追溯性落在“原文片段是否支持答案”上，而不是结构化字段能否字面对上；
- 更换提取模型、调整 Schema、扩充谓词目录，都只需重建索引，不用迁移数据。

### 3.2 借鉴海马体的三层结构

海马体本身主要是索引。新经历在这里被快速编码，之后通过回放和巩固，转成新皮层里的语义知识。对应到系统：

| 层 | 类比 | 内容 | 处理方式 |
| --- | --- | --- | --- |
| 事件层 | 感觉输入 | 原始对话和活动，只追加不修改 | 实时，零模型或极少模型 |
| 情景层 | 海马体 | 按会话或话题切分的情景，附带摘要、实体和向量 | 近实时，用便宜的模型 |
| 语义层 | 新皮层 | 事实、偏好、习惯、关系、项目与意图、用户画像 | 离线巩固，用好的模型，附带证据链 |

短期、中期、长期记忆**由所处的处理阶段决定**，而不是一个标签。当前的 `RetentionTier` 基本只是一个字段，见 `architecture/retention.md`。

### 3.3 模型负责理解和判断，代码负责记账和执行

- **写入侧**：模型只做轻量的语义提取，另外在少数有针对性的地方做判断；时间换算、校验、准入、合并交给代码。
- **召回侧**：用语义检索和蕴含判断取代句式规则。
- **硬约束仍由代码保证**：必须精确链接到原文、值必须唯一、冲突时不选边。

### 3.4 从“把关答案”改为“证据分级”（2026-09-29 确定）

现在的做法要求宿主草稿与 `safe_answer` 逐字一致才放行，但宿主不调用校验时，MCP 根本拦不住；而且只有整理入库的记忆才能作答，提取一出错，原文明明在库里也答不出来。改为按 3.1 以原文为本：已保存的用户原话都可以作为答案证据，结构化记忆只负责检索和排序，每条证据标注等级，由宿主据此作答，校验改为可选。

分工边界，防止退回句式规则：

- **代码只核验机械可验证的东西**：原文片段是否逐字存在、来源归属、任务隔离、时间先后。
- **任何语义问题一律交给模型**：是不是同一个主体、是否被后来的话更正、是假设还是提问还是转述，都由模型判断，不为某种句式写特判。模型答不好，就改提示词或换模型角色，而不是加规则。
- **等级只做标注，不做分支**：等级（例如“已整理核准”与“来自原文、未整理”）原样告诉调用方，代码不据此触发任何特殊处理逻辑。

等级的具体名称，以及 `memory_validate_answer` 是否保留为可选步骤，在实现时按评测结果确定。

## 4. 模型：混合部署，按角色配置

现在 `src/openai.rs` 把请求构造、提示词、Schema 和具体服务商写在一起，推理接入点是一个硬编码常量。改为按角色抽象：

| 角色 | 建议默认 | 说明 |
| --- | --- | --- |
| `embed` 向量化 | 本地（如 bge-m3） | 调用最频繁、最便宜，放本地收益最大 |
| `classify` 问题分类与路由 | 本地小模型 | 对延迟敏感 |
| `extract` 提取 | 可配置 | 在实时链路里，要求轻量 |
| `verify` 蕴含判断 | 本地或云端 | 只回答“是否支持” |
| `consolidate` 离线巩固 | 云端大模型 | 离线运行，质量要求最高 |

- 本地模型统一走 OpenAI 兼容协议，支持 Ollama、llama.cpp、vLLM。
- **隐私路由**：可按敏感等级分流，例如健康、财务相关内容只发往本地模型。“完全离线”模式下退回只用 FTS、不调用模型，也就是现有 `local` 模式的底线。
- 提示词和 Schema 要能在小模型上运行，这也是精简提取 Schema 的又一个理由。
- 评测集要能在不同配置组合下运行，并输出一张质量、延迟、成本的对照表。调用预算细分到每个角色。

## 5. 第一批数据源：用户与 AI 的对话

1. **纳入助手回复，但区分立场**：助手说的话本身不算用户事实。只有用户明确采纳或确认之后，才生成一条“决定”类记忆，证据同时引用助手的那句话和用户确认的那句话。
2. **用户消息不等于用户陈述**：用户粘贴的文章、日志、他人的聊天记录，要识别出来，归为“用户看到的内容”。这是错误事实和记忆投毒的主要入口。
3. **两种采集方式并存，重心逐步移向导入**：
   - 实时 MCP：依赖宿主主动调用，天然不可靠；
   - 导入对话导出文件（ChatGPT、Claude 等）：不依赖宿主，能一次带来几个月的真实数据，可用于验证离线巩固，也可在脱敏后作为评测素材；
   - 两种方式采到的数据按“平台 + 会话 ID + 消息 ID”去重，沿用现有的幂等回执；
   - 下一步做浏览器扩展，直接采集各 AI 聊天网页。
4. **显著性过滤**：对话里大部分内容是任务性的（写代码、改文案），需要判断哪些值得记。
5. **项目与意图记忆**：从对话中最值得提取的，通常是“用户在做什么、卡在哪里、做了什么决定”。
6. **按对话切分情景**：先按会话加话题变化来切，不追求通用方案。

## 6. 需要补齐的能力

### 6.1 记忆类型

| 类型 | 现状 | 补充 |
| --- | --- | --- |
| 意图、计划（前瞻记忆） | 明确不入库 | 作为独立类型，带状态（进行中、已完成、已放弃）和时间，不和已发生的事实混在一起 |
| 习惯、流程（程序性记忆） | 无 | 记录用户通常怎么做一件事 |
| 用户画像 | 只有 bootstrap 返回全局约束和风格 | 一份持续维护、用户可查看和编辑的结构化摘要，在会话开始时注入 |
| 关系 | 只有 IS-A 边和别名精确匹配 | 建实体图：人、组织、项目、地点及它们之间的关系，支持合并与拆分 |

### 6.2 区分信息的来源类型

| 来源类别 | 例子 | 能推出什么 |
| --- | --- | --- |
| 用户陈述 | “我对花生过敏” | 可以作为事实 |
| 用户行为 | 购买、作息规律 | 只能作为推断，需要置信度、累积证据和反证 |
| 用户看到的内容 | 浏览过的文章、粘贴的内容 | 不代表用户相信或采纳 |
| 他人陈述 | 同事在邮件里说的话 | 是关于用户的断言，但不是用户说的 |

推断出的记忆要和用户陈述分开存储、分开呈现，并能说明“为什么这样认为”。

### 6.3 能力短板（见 `architecture/capabilities.md`）

- **多会话推理**：模型只给出查询计划，代码在结构化记忆上计数、列举、求和，每一项都链接到原文。
- **时间推理**：计算时间差，对事件排序；`reference` 不为空的记忆不能在当前查询中完全不可见。
- **知识更新**：同一语义槽出现不同值时，把新旧两段原文交给模型，判断是现实变化、纠错、可以并存，还是无法判断。
- **留存**：ShortTerm 设置默认有效期；离线巩固负责把到期状态写回、合并近义表述的强化、归纳偏好。归纳结果只作为建议，由用户确认后才写入。

### 6.4 服务层

- 在 MCP 之外提供 HTTP 接口和 SDK。
- 从被动召回转向主动提供：根据当前上下文主动带出相关记忆，或到期提醒。
- 管理上下文预算，在画像、相关记忆和原文证据之间取舍，并标注可信度。

### 6.5 隐私、安全与用户控制

- 本地优先，存储加密，密钥放在系统钥匙串。明确哪些数据会发往云端。
- 对健康、财务、位置、第三方隐私等敏感信息分级，默认不对外提供，并支持脱敏。
- 按消费方授权：不同的 AI 工具看到不同范围的记忆，例如工作和私人分开。
- 防投毒：外部内容只能生成“用户看到了什么”这一类记忆，不能生成关于用户的事实断言。
- 用户可以查看、修改、删除、导出记忆，可以暂停采集、指定“这条别记”、按来源整体清除，符合 GDPR 和个人信息保护法（PIPL）。Inspector 要演进为面向用户的记忆管理界面。

### 6.6 评测

- **常驻评测集**：100 到 200 条，包括自建中文样本、LongMemEval 子集、LoCoMo，以及 S6 的失败样本。离线部分用录制的模型响应回放，接入 `cargo test`；真实模型的评测定期运行。所有改动都看同一个分数，不再为单个样本新开目录。
- **个性化指标**：回答是否用上了相关偏好、是否避开了约束，主动提醒的准确率和打扰率。
- **长期仿真**：用合成用户生成几个月的对话流，测试巩固、遗忘、实体消解和画像漂移。
- **成本与延迟**：统计每位用户每天的模型费用、存储增长和召回 P95 延迟，并按模型配置分别输出。

### 6.7 工程基础

- 把整份 JSON 快照拆成按记录存储；事件日志、向量索引、实体图分开存放。
- 异步任务队列，用于导入、巩固和重建索引；解除全局 `Mutex` 串行。
- 为 Schema 和提取器记录版本，保证语义层可以从事件层整体重建。
- 多设备同步（M4 前确定形态）。
- 规范 git 提交。现在仓库只有一个 commit，而架构文档引用了 4 个不同的提交号。

## 7. 里程碑

原则：**先通过 MCP 把记忆质量做扎实，再扩展采集和应用。** 按目前的写入可靠性，数据越多，错误记忆越多，用户信任会先崩溃。

### M1 可靠内核

| 任务 | 说明 |
| --- | --- |
| 常驻评测集 | 从 S6 的失败样本和 `tests/recorded_llm_cases.rs` 起步 |
| 写入值必须能在原文中落地 | 文本或数字值归一化后必须出现在引用片段中；布尔值要求原文有肯定或否定的表达。通用规则，不为具体样本写特判 |
| 条件不匹配时降级 | 查询没提到的活动条件，从“过滤掉”改为“标注适用条件” |
| 默认召回模式改为 `local` | `legacy` 模式无法核准任何答案 |
| 模型角色抽象 | 按角色配置服务商，接入本地 OpenAI 兼容端点 |
| 精简提取 | 时间只摘原文；去掉次要字段；按风险触发核验；纯查询跳过提取（MEM-001） |
| 混合检索 | FTS 加向量检索，结果融合 |
| 问题分类与蕴含核准 | 用模型取代 `parse_question` 和字面核对；以评测分数为依据，逐步删除句式规则 |
| 更新判定参考旧记忆 | 同槽不同值时，交给模型判断 |

### M2 对话数据源完善

- 导入对话导出文件；
- 区分助手回复的立场，并处理“用户确认”；
- 识别用户粘贴的内容；
- 实时采集和导入之间去重；
- 显著性过滤。

### M3 分层记忆

- 按对话切分情景，建立情景层；
- 离线巩固；
- 用户画像、项目与意图记忆、实体图；
- 留存机制（默认有效期、状态写回）；
- 存储重构。

### M4 独立应用

- 面向用户的记忆管理界面；
- 浏览器扩展采集；
- 加密、隐私路由、按消费方授权；
- 主动提醒；
- 开放 API；
- 多设备同步。
